# 多开 SaaS 商城 — 产品设计（一）总体方案

> 对标产品：萤火商城 V2 多开版（PHP7.4 + ThinkPHP6 + uni-app + Ant Design Vue，`/admin` 超管 + `/store` 商户双后台）
> 本产品形态：**纯多开 B2C**（每个租户一套独立商城）
> 技术栈：**Java（Spring Boot）+ Vue3 + uni-app**
> 文档版本：v0.1 ｜ 状态：待评审

---

## 1. 产品定位

面向"给中小商家开独立商城"的服务商，提供一套**一次部署、无限开店**的 SaaS 商城系统。

平台方（我们/服务商）在超管后台点几下就能开出一个全新商城，商家拿到的是一套**看起来完全属于自己**的商城：独立小程序、独立域名、独立数据、独立品牌、独立收款账户。商家之间互不可见、互不影响。

一句话：**萤火多开版的能力，用 Java 重写并补齐 SaaS 运营层。**

### 1.1 与两种相邻形态的区别

| 形态 | 谁在卖货 | 钱流向谁 | 本产品 |
|---|---|---|---|
| 单商户商城 | 一个老板 | 老板 | ❌ 只是本产品的一个租户 |
| **多开 SaaS（本产品）** | 每个租户各自卖各自的 | **直接进各租户自己的商户号** | ✅ |
| B2B2C 平台（多商户入驻） | 平台招商，多店铺同台竞争 | 先进平台、再分账给店铺 | ❌ 二期预留，见 §6.3 |

### 1.2 我们靠什么赚钱

平台方收的是**软件订阅费**，不碰租户的交易资金。这条边界决定了整套架构（见 §5.3 支付方案）：

- 套餐年费/月费（基础版 / 标准版 / 旗舰版）
- 增值项：独立域名、小程序代上架服务、短信包、存储扩容、功能插件
- 定制开发与代运营（线下）

## 3. 租户模型（多开的本质）

### 3.1 一个"商城"包含什么

在本系统里，**一个租户 = 一个 shop（商城）**，创建商城时同时初始化：

1. 商城主体信息（名称、logo、行业、联系人）
2. 一个**超级店主账号**（`store_user`，不可删除、拥有全部权限）
3. 一套**默认数据种子**：默认商品分类、默认运费模板、默认页面装修模板、默认交易设置、默认会员等级、默认协议文本
4. 一份**套餐授权**（`shop_package`：功能菜单集合 + 配额 + 有效期）
5. 一个**访问入口**：`{code}.shop.com` 泛域名，后续可绑定自有域名
6. 一个**独立文件空间**（存储路径以 shop_id 分目录）

### 3.2 隔离策略

| 维度 | 策略 |
|---|---|
| 数据 | 单库多租户，业务表统一带 `shop_id`，框架层自动注入过滤（详见文档三 §2） |
| 账号 | 商户账号、消费者账号均在租户内唯一；同一手机号可在不同租户各注册一个消费者身份 |
| 文件 | 对象存储按 `shop/{shop_id}/...` 分目录；支持租户使用**自己的** OSS 配置 |
| 缓存 | Redis key 强制 `t:{shop_id}:` 前缀 |
| 域名 | 泛域名 + 自定义域名，均解析到同一集群，由网关按 Host 识别租户 |
| 客户端 | 小程序/公众号/APP 各自独立 appid，见 §5.2 |
| 收款 | 各租户各自的微信/支付宝商户号，资金不经过平台，见 §5.3 |
| 资源 | 套餐配额（商品数、员工数、存储、短信条数、活动数）+ 接口限流按租户维度 |

### 3.3 租户生命周期

```
  [试用] ──开通付费──> [正常] ──到期前7/3/1天──> [到期预警]
     │                   │                          │
   到期未付               │违规                    到期未续费
     ▼                   ▼                          ▼
  [已过期] <──────────[已停用]                   [已过期]
     │                                             │
   续费 ─────────────────────────────────────────> [正常]
     │
   超过保留期(默认90天) ──> [归档] ──> 数据导出后物理清理
```

状态语义（重要，直接影响用户端表现）：

| 状态 | 商户后台 | 用户端小程序/H5 | 定时任务 |
|---|---|---|---|
| 试用 trial | 可用（部分功能锁） | 正常 | 正常 |
| 正常 normal | 可用 | 正常 | 正常 |
| 到期预警 | 可用 + 全局到期横幅 | 正常 | 正常 |
| 已过期 expired | **只能登录看数据 + 续费，不能下架/改价/发货？** → 设计选择：**保留发货与售后能力**，禁止新增商品/开活动/装修 | 停止交易：可浏览、不可下单，提示"店铺休息中" | 仅保留订单收尾任务 |
| 已停用 disabled | 不可登录 | 直接不可访问 | 全停 |
| 归档 archived | 不可登录 | 不可访问 | 全停，数据只读备份 |

> 设计取舍：过期后**仍允许发货和退款**。因为消费者已经付过钱了，直接锁死会把 SaaS 的商业纠纷转嫁到消费者身上，租户投诉率会很高。锁的是"增长类"功能，这对续费的驱动力已经足够。

### 3.4 套餐（Package）

套餐 = **功能菜单集合 + 配额上限 + 周期价格**。

```yaml
package:
  name: 标准版
  price: { month: 299, quarter: 799, year: 2680 }
  menus:                      # 控制商户后台菜单可见性 + 后端接口鉴权
    - goods.*
    - order.*
    - marketing.coupon
    - marketing.seckill
    - distribution.*          # 分销
    - store.offline           # 门店自提
    # 未包含 marketing.bargain / apps.printer 等
  quota:
    goods_max: 5000
    staff_max: 10
    storage_mb: 20480
    sms_month: 1000
    seckill_active_max: 20
    diy_page_max: 30
  addon_allowed: [domain, sms_pack, storage_pack, app_build]
```

要点：
- 套餐变更（升级/降级）需做**配额校验**：降级时若当前商品数已超新套餐上限，不阻断存量数据，但禁止新增（软限制），并在后台明确提示。硬删数据永远不做。
- 套餐字段做**快照**：租户开通时把套餐内容快照到 `shop_package` 表，之后平台改套餐模板不影响已开通租户（除非平台显式"同步"）。这是 SaaS 计费系统最容易踩的坑。

## 5. 架构关键决策

### 5.1 整体架构

```
                    ┌──────────────────────────────────────┐
   小程序A/B/C ────> │  Nginx / SLB                         │
   H5 / APP    ────> │  按 Host 或 AppID 识别租户            │
   自定义域名   ────> └───────────────┬──────────────────────┘
                                     ▼
                    ┌──────────────────────────────────────┐
                    │  Spring Boot 应用（单体分模块起步）      │
                    │  ┌────────┬────────┬────────┐         │
                    │  │ admin  │ store  │  api   │  各自    │
                    │  │ 超管接口│商户接口 │用户端接口│  独立   │
                    │  └────────┴────────┴────────┘  过滤链  │
                    │  ─────────────────────────────────    │
                    │  TenantContext（租户上下文，贯穿全链路） │
                    │  ─────────────────────────────────    │
                    │  domain: goods/order/pay/marketing/   │
                    │          distribution/member/diy/...  │
                    │  ─────────────────────────────────    │
                    │  infra: mp-tenant / cache / mq /      │
                    │         oss / sms / wechat-open       │
                    └───────┬──────────────┬───────────────┘
                            ▼              ▼
                   MySQL(单库多租户)    Redis / RocketMQ / XXL-Job
                            │
                   预留：按 shop_id 分库分组（见 §6.2）
```

**为什么单体分模块而不是一上来微服务**：多开 SaaS 的负载模型是"租户多、单租户小"，横向复制无状态应用节点就能扩，拆微服务只会把租户上下文透传、分布式事务、部署复杂度全部提前引爆。留好模块边界（`domain` 包不互相反向依赖），需要时再拆订单/支付。

### 5.2 客户端多开：小程序怎么"一店一小程序"

这是多开 SaaS 最核心也最容易低估的一块。提供**两种模式**，租户二选一：

**模式 A：自填 AppID（简单模式，MVP 必做）**
租户自己注册小程序、自己在商户后台填 AppID + Secret、自己下载我们生成的小程序代码包上传发布，或由平台代为上传。
- 优点：零门槛上线，不依赖微信开放平台资质
- 缺点：每次系统升级都要重新上传每一个小程序，租户多了就是灾难

**模式 B：微信第三方平台托管（★多开核心能力，一期后半程做）**
平台注册**微信开放平台第三方平台**，租户扫码授权后，平台可以"代小程序实现业务"：
- 代上传代码（一份代码模板 + 每租户不同的 `ext.json` 注入 shop_id / 域名 / 主题色）
- 代提交审核、代发布、代回退
- 代配置服务器域名、业务域名
- **批量升级**：平台发布新版本模板 → 一键给 N 个租户排队上传+提审

关键设计：
- 代码模板库：维护 `template_id` 与版本说明，`ext.json` 是租户差异的唯一注入点，业务代码本身**不允许**有租户分支
- 提审是异步且可能被驳回的 → 建 `mp_release_task` 任务表 + 状态机（待上传/已上传/待审/审核中/审核通过/已发布/驳回），驳回原因回写给租户可见
- 微信侧有**每日提审次数**与接口频率限制 → 任务队列必须限速、可暂停、可重试

**公众号 / H5 / APP**
- 公众号：同样支持自填 + 第三方平台授权；主要用于网页授权登录、模板消息、菜单配置
- H5：泛域名开箱即用，自定义域名走 §5.4
- APP：uni-app 云打包，商户后台提交打包任务（图标、启动图、应用名、包名、证书），平台侧排队构建，产出 apk/ipa 供租户下载上架

### 5.3 支付：资金必须直达租户

三种模式，按租户资质与平台定位选：

| 模式 | 资金路径 | 平台角色 | 适用 |
|---|---|---|---|
| **① 租户自有商户号（默认，MVP 必做）** | 消费者 → 租户商户号 | 只提供软件，不碰钱 | 绝大多数场景，合规风险最低 |
| ② 服务商模式（特约商户） | 消费者 → 租户特约商户号 | 平台是服务商，可代进件、可收服务费分账 | 平台想做支付分润 |
| ③ 平台收款再结算 | 消费者 → 平台 → 提现给租户 | **平台在做"二清"** | ❌ **不做**，无牌照属违规 |

设计要点：
- 支付参数（mchid、apiv3key、证书）**加密存储**，商户后台只显示掩码，不可回显明文
- 支付回调地址统一走平台域名 `/notify/wxpay/{shop_id}/{token}`，由平台按 shop_id 路由验签
- 退款走原路，退款资金从租户商户号出，平台只发起指令
- 余额支付、货到付款为纯内部账，不涉及资金通道

### 5.4 域名与访问

- 泛域名：`*.shop.com` 一张泛域名证书搞定，开店即用
- 自定义域名：租户填域名 → 平台给出 CNAME → 校验解析 → 自动申请 Let's Encrypt 证书（ACME DNS/HTTP 校验）→ 网关热加载
- 小程序业务域名需在微信侧配置，模式 B 可由第三方平台接口代配

### 5.5 装修引擎（DIY）

页面 = 一份 JSON Schema，商户后台可视化拖拽产出，端上按组件名渲染。

```jsonc
{
  "page": { "name": "首页", "title": "XX商城", "shareTitle": "...", "bgColor": "#f8f8f8" },
  "items": [
    { "type": "banner",  "style": {...}, "data": [{ "imgUrl": "...", "link": {...} }] },
    { "type": "navBar",  "style": { "rowNum": 4 }, "data": [...] },
    { "type": "goods",   "style": { "display": "list", "column": 2, "show": ["name","price"] },
      "data": { "source": "category", "categoryId": 12, "limit": 6 } },
    { "type": "coupon" }, { "type": "seckill" }, { "type": "richText" }, { "type": "blank" }
  ]
}
```

要点：
- **组件白名单由套餐控制**（如"秒杀组件"仅标准版以上可拖）
- 商品/优惠券等组件只存**引用 ID**，端上取数时实时查，避免装修数据与商品数据脱节
- 支持页面模板库：平台预置若干行业模板（服饰/生鲜/美妆），租户一键套用；租户自己也能存为模板
- 版本与预览：草稿/发布分离，扫码真机预览，支持回滚

### 5.6 数据看板与统计

- 实时数据用 Redis 计数器（今日订单/销售额），T+1 明细走离线汇总表 `stat_shop_daily`
- 平台侧的 GMV 汇总从各租户日汇总表二次聚合，**不做跨租户实时大查询**

## 6. 演进与预留

### 6.1 里程碑规划

| 阶段 | 目标 | 主要内容 | 预估 |
|---|---|---|---|
| **M0 基座** | 能开店、能登录 | 多租户框架、TenantContext、RBAC、超管建店/套餐/到期、商户后台骨架、文件存储、字典/地区 | 3~4 周 |
| **M1 交易闭环** | 能卖出第一单 | 商品(单/多规格)、分类、购物车、下单、微信支付(自有商户号)、运费模板、订单全流程、售后、物流查询、消费者端基础页面 | 6~8 周 |
| **M2 会员与营销** | 能做活动 | 会员等级/积分/余额充值、优惠券、满减、限时折扣、拼团、秒杀、砍价、签到、评价 | 6~8 周 |
| **M3 分销与门店** | 能裂变 | 分销体系(层级/佣金/提现/海报)、自提门店与核销、店员权限 | 4~5 周 |
| **M4 装修与多端** | 能像自己的店 | DIY 装修引擎 + 组件库、模板市场、H5/公众号、APP 打包、自定义域名 | 5~6 周 |
| **M5 SaaS 运营** | 能规模化交付 | 微信第三方平台托管、批量代上传/提审/发布、订购与续费在线支付、发票、用量统计、运维中心、数据备份 | 5~6 周 |

> M1 结束即可小范围试点交付（用泛域名 + 自填 AppID 模式）；M5 结束才具备"规模化开店"的运营效率。

### 6.2 分库预留

单库多租户在几千租户内完全够用。触发拆分的信号：单表超 5000 万行、或出现需要独占资源的大客户。

预留方式：
- 所有业务表**已带 shop_id**，天然可按 shop_id 路由
- 引入 `shop_shard` 路由表（shop_id → 数据源），应用层用 ShardingSphere / 动态数据源按租户选库
- 大客户可直接"迁库独占"：停机窗口内按 shop_id 导出导入 + 切路由

### 6.3 B2B2C 预留

若未来某个租户要做招商平台：
- 在租户内引入 `seller_id`（店铺）层级，商品/订单挂 seller_id
- 订单拆单（按 seller 拆子订单）+ 分账（微信服务商分账能力）
- 结算周期、平台佣金、店铺入驻审核、店铺装修

不在一期做，但**订单表预留 `seller_id` 字段与拆单父子结构**（`order` / `order_sub`），避免二期做表结构大手术。

## 7. 非功能性要求

| 项 | 目标 |
|---|---|
| 性能 | 商品列表 P95 < 300ms；下单 P95 < 800ms；单节点支撑 500 QPS |
| 容量 | 一期支撑 1000 租户 / 500 万商品 / 日订单 10 万 |
| 可用性 | 99.9%；应用无状态可水平扩；MySQL 主从；Redis 哨兵 |
| 安全 | 租户越权是头号风险（见文档三 §2.4）；支付密钥加密；越权测试进 CI；操作日志全留痕 |
| 合规 | 不做资金二清；用户隐私协议与信息收集清单；小程序类目与内容审核；数据导出与删除响应 |
| 可观测 | 按租户维度的接口耗时/错误率；慢 SQL；队列积压；到期与配额告警 |
| 升级 | 全租户共用一套代码，DB 变更用 Flyway；小程序端批量升级见 §5.2 |

## 8. 待确认清单

1. 平台是否申请**微信开放平台第三方平台**资质（决定 M5 托管能力能否落地，审核周期约 1~2 周，需企业主体）
2. 支付是否走**服务商模式**（决定平台能否吃支付分润，需微信服务商资质）
3. APP 打包是走 **DCloud 云打包**（需付费/证书）还是自建构建机
4. 短信、物流查询等第三方通道：平台统一采买转售给租户，还是租户自填自己的 key（建议：两者都支持，默认用平台的并计入配额）
5. 是否需要**私有化部署**版本（会影响授权校验、许可证与升级机制设计）
