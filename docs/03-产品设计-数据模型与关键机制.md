**三套 API 分离的理由**：鉴权主体不同（平台管理员 / 商户员工 / 消费者）、租户解析方式不同（显式指定 / token 携带 / 域名或 appid 推断）、限流策略不同。分成三个 Controller 层 + 三条过滤链，比在一套里用注解区分要清晰得多。

## 2. 多租户实现（最关键的部分）

### 2.1 租户上下文

```java
public final class TenantContext {
    private static final ThreadLocal<Long> SHOP_ID = new TransmittableThreadLocal<>();
    private static final ThreadLocal<Boolean> IGNORE = new TransmittableThreadLocal<>();

    public static Long get()            { return SHOP_ID.get(); }
    public static void set(Long shopId) { SHOP_ID.set(shopId); }
    public static void clear()          { SHOP_ID.remove(); IGNORE.remove(); }

    /** 仅平台超管的跨租户查询可用，必须显式声明 */
    public static <T> T ignoreTenant(Supplier<T> fn) { ... }
}
```
用 `TransmittableThreadLocal` 是因为异步任务、线程池、MQ 消费都要透传租户；`InheritableThreadLocal` 在线程池场景会串号——这是多租户系统最经典的生产事故。

### 2.2 租户识别来源（按端）

| 端 | 识别方式 | 兜底 |
|---|---|---|
| `/store/**` | JWT claim 中的 `shopId` | 无 → 401 |
| `/api/**` | ① 请求头 `X-Shop-Id`（小程序由 ext.json 注入）② Host 反查域名表 ③ 小程序 AppID 反查 | 无 → 400 |
| `/admin/**` | 默认无租户；操作单个租户时由**路径参数**显式指定并校验平台权限 | — |
| 支付回调 | 回调路径中的 `{shop_id}` + 签名校验 | — |
| MQ / 定时任务 | 消息体携带 `shopId`；全租户任务按 shop 列表循环 set/clear | — |

### 2.3 数据层自动隔离

MyBatis-Plus `TenantLineInnerInterceptor`：
- 所有业务表 SQL 自动拼 `shop_id = ?`，INSERT 自动填充
- **忽略表白名单**：`sys_*`、`shop`、`shop_package`、`platform_*`、`region`、`express_company` 等平台级表
- 忽略 SQL 白名单：仅限平台统计等显式声明的 Mapper 方法（加 `@IgnoreTenant` 注解）

### 2.4 越权防御（P0 安全红线）

自动注入 `shop_id` 只防了"查漏"，防不了"改错"。补三道：

1. **写操作二次校验**：`update/delete` 的 where 条件必须含 shop_id（拦截器强制，缺失直接抛异常而非静默放行）
2. **ID 归属校验**：所有按主键操作的接口，Service 层统一走 `getByIdWithTenant(id)`，查不到即 404，不允许 `getById` 裸用（用 ArchUnit 在 CI 里做静态检查）
3. **自动化越权测试**：CI 中跑租户 A 的 token 访问租户 B 的资源 ID，覆盖所有 `/store/**` 接口，任一返回非 403/404 即构建失败

### 2.5 缓存与文件隔离

```java
// key 由框架统一生成，业务侧无法绕过
cacheKey = "t:" + shopId + ":goods:detail:" + goodsId
ossPath  = "shop/" + shopId + "/" + yyyyMM + "/" + uuid + ext
```

## 3. 核心数据模型

> 约定：所有业务表含 `id`(bigint 雪花)、`shop_id`(bigint, 索引首列)、`create_time`、`update_time`、`is_delete`(逻辑删除)。
> 金额一律 `decimal(10,2)`，禁止 float/double。
> 联合索引一律 `(shop_id, xxx)` 开头。

## 4. 价格计算引擎（单一入口）

下单预览、正式下单、修改订单、售后退款金额计算——**必须共用一套代码**。任何一处单独算价，最终都会出现"预览 98 元、实付 102 元"的投诉。

```java
public interface PriceCalculator {
    /** 输入购物项 + 用户 + 优惠选择，输出完整价格明细 */
    OrderPriceResult calculate(PriceContext ctx);
}
```

责任链顺序（固定，不可配置乱序）：

```
1. BasePriceHandler        原价小计（按 SKU）
2. ActivityPriceHandler    秒杀 / 拼团 / 限时折扣（互斥，取活动价替换原价）
3. MemberDiscountHandler   会员等级折扣（活动商品默认不叠加，可配置）
4. FullReduceHandler       满减 / 满件折
5. CouponHandler           优惠券（校验适用范围、门槛按"参与商品实付小计"判定）
6. PointsHandler           积分抵扣（受最高抵扣比例限制）
7. FreightHandler          运费（运费模板 + 包邮规则 + 自提免运费）
8. RoundingHandler         分摊与舍入
```

**优惠分摊是必须做的**（不做的话部分退款一定算错）：每一笔优惠都要按商品实付比例分摊到 `order_goods`，退款时按分摊后的金额退。`order_goods` 上存 `discount_detail(json)` 记录每项优惠的分摊额。

## 5. 库存与并发

| 场景 | 方案 |
|---|---|
| 普通下单 | DB 乐观扣减：`update goods_sku set stock = stock - #{n} where id=? and shop_id=? and stock >= #{n}`，影响行数 0 即库存不足 |
| 秒杀 | Redis 预扣（Lua 原子脚本）拦掉绝大部分流量 → 入队 → 落库扣减；失败回补 Redis |
| 超时关单 | RocketMQ 延时消息（按交易设置的分钟数）→ 消费时校验订单仍为待付款 → 关单回滚库存 |
| 退款回滚 | 售后退款成功后按 `order_goods.total_num` 回补库存（可配置是否回补） |

超卖是电商系统唯一"用户会截图发朋友圈"的 bug，秒杀链路要单独做压测。

## 8. 接口与鉴权规范

```
/admin/**   平台管理员    JWT(platform)    权限：platform_menu 码
/store/**   商户员工      JWT(store, 含shopId)  权限：store_role menu 码 + 套餐 menus 交集
/api/**     消费者        JWT(user, 含shopId) 或 游客(仅浏览)
/notify/**  第三方回调    签名校验，无 JWT
```

**套餐权限与角色权限的关系**：最终可用菜单 = `套餐 menus` ∩ `角色 menu_ids`。后端接口鉴权两者都要校验——只在前端隐藏菜单是常见的越权漏洞来源。

统一响应：
```json
{ "code": 0, "msg": "ok", "data": {}, "traceId": "..." }
```
错误码分段：1xxxx 通用 / 2xxxx 租户与套餐（如 20001 套餐已过期、20002 配额已满）/ 3xxxx 商品 / 4xxxx 订单 / 5xxxx 支付 / 6xxxx 营销。

## 9. 敏感配置加密

租户的微信支付 `mchid`/`apiv3key`/证书、OSS AK/SK、短信 key，统一用 AES-256 加密后入库，密钥走环境变量/KMS，**不允许回显明文**（前端只展示 `mch_****1234`，更新时全量重填）。这条如果一开始不做，后面租户数量上来了就没法补。

## 10. 部署形态

```
                 SLB
                  │
     ┌────────────┼────────────┐
     ▼            ▼            ▼
  app-node1   app-node2   app-node3      （无状态，含 admin/store/api）
     └────────────┼────────────┘
                  │
     ┌────────────┼─────────────┬──────────────┐
     ▼            ▼             ▼              ▼
  MySQL 主从   Redis 哨兵   RocketMQ      OSS/COS
                  │
            job-node（XXL-Job 执行器，可与 app 合并）
            mp-node （微信第三方平台服务，需固定出口IP+独立域名）
```

- `shop-mp` 建议独立部署：微信第三方平台的授权回调、票据推送有固定 URL 与 IP 白名单要求，独立后升级主应用不影响托管服务
- 数据库变更用 Flyway，禁止手工改线上表结构
- 灰度：新版本先切 5% 流量或指定测试租户（网关按 shop_id 路由）

---

## 11. 开发顺序建议（对应 M0~M5）

1. **M0**：`shop-framework/tenant` 先写完并把越权测试挂进 CI → 平台 RBAC → 建店流程与种子数据 → 商户后台登录与菜单（套餐∩角色）
2. **M1**：商品（含多规格）→ 购物车 → **价格计算引擎骨架** → 下单 → 微信支付 → 订单流程 → 售后（含优惠分摊退款）→ uni-app 交易链路
3. **M2**：会员/积分/余额 → 优惠券 → 满减 → 秒杀 → 拼团 → 砍价（每个玩法都接入价格引擎的 Handler，不要另起炉灶）
4. **M3**：分销 → 门店自提核销
5. **M4**：DIY 引擎（先定 schema 与组件协议，再做编辑器）→ 多端 → 自定义域名
6. **M5**：微信第三方平台托管 → 批量发布 → 在线订购续费 → 运维中心

> 第 1 步的越权测试和第 2 步的价格引擎，是这套系统里"补做成本 10 倍"的两件事，务必前置。
