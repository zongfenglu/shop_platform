# 05 - 部署运维手册（Docker Compose 全栈）

本文覆盖生产/预发环境的容器化部署、日常运维与排障。本地开发环境见 `README.md`「快速开始」。

## 1. 两套 compose 的分工

| 文件 | 用途 | 容器内容 |
| --- | --- | --- |
| `docker/docker-compose.yml` | 本地 / 试点 | **一个 JVM**（`shop-app`：超管+商户+C端+定时任务+微信回调）+ MySQL + Redis + 三个前端。RocketMQ 挂 `mq` profile，默认不启 |
| `docker/docker-compose.prod.yml` | 生产 / 预发 | 仍按模块拆分：admin/store/client/job + 前端 + MySQL/Redis/RocketMQ |

两者项目名不同（`shop-platform` / `shop-platform-prod`），卷和网络互不干扰，同一台机器可以并存。

## 2. 首次部署

前置条件：目标机器装好 Docker Engine 24+ 与 Docker Compose v2（`docker compose version` 能输出）。**不需要**装 JDK、Maven、Node —— 全部在构建阶段的容器里完成。

```bash
git clone <repo> && cd shop_platform

# 1. 环境变量
cp docker/.env.prod.example docker/.env
vi docker/.env      # 所有 CHANGE_ME 必须替换

# 2. 构建 + 启动（首次构建要下载全部 Maven 依赖，10~20 分钟正常）
docker compose -f docker/docker-compose.prod.yml up -d --build

# 3. 等 admin-api healthy（它跑完 Flyway 迁移，其余应用才会启动）
docker compose -f docker/docker-compose.prod.yml ps

# 4. XXL-Job 调度中心初始化（只需一次）
curl -fsSL -o /tmp/tables_xxl_job.sql \
  https://raw.githubusercontent.com/xuxueli/xxl-job/2.4.2/doc/db/tables_xxl_job.sql
source docker/.env
docker exec -i shop-prod-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" < /tmp/tables_xxl_job.sql
docker compose -f docker/docker-compose.prod.yml restart xxl-job-admin
```

> 国内网络访问 `raw.githubusercontent.com` 常被重置，可用镜像：
> `https://ghproxy.net/https://raw.githubusercontent.com/xuxueli/xxl-job/2.4.2/doc/db/tables_xxl_job.sql`

### 生成密钥

```bash
openssl rand -base64 48   # JWT_SECRET
openssl rand -base64 32   # AES_KEY
openssl rand -hex 16      # XXL_JOB_ACCESS_TOKEN / 数据库密码
```

`AES_KEY` 用于加密各租户的微信支付商户凭证。**上线后不能更换** —— 换了之后已入库的凭证全部解不开，所有租户收款失效。要轮换必须先用旧密钥批量解密、再用新密钥重新加密。

> `.env` 里含空格的值（四个 `*_JAVA_OPTS`）必须加引号。compose 自己两种写法都能解析，但文档里多处用 `source docker/.env` 把变量导进 shell，不加引号时 bash 会把 `-Xmx1g` 当命令执行并报 `command not found`。

## 3. 前端上线

`shop-ui/admin`、`shop-ui/store`、`shop-uniapp` 目前是空目录，因此三个前端服务归在 `frontend` profile，默认不构建。前端源码落地后：

```bash
docker compose -f docker/docker-compose.prod.yml --profile frontend up -d --build
```

构建假设（前端脚手架搭起来时对齐这几点，否则要改 `Dockerfile.frontend`）：

- 产物目录是 `dist/`
- Vue 后台的构建命令是 `npm run build`；uni-app H5 是 `npm run build:h5`（compose 里通过 `BUILD_CMD` 传入）
- 后台前端用 Vue Router **history** 模式（Nginx 已配 `try_files ... /index.html`）
- 前端调用后端用**同源相对路径**：admin 打 `/admin/**`、store 打 `/store/**`、H5 打 `/api/**`，由 Nginx 反代到对应容器。不要在前端写死后端域名+端口，否则跨域和多租户域名都要额外处理。

## 4. 日常运维

```bash
cd /path/to/shop_platform
C=docker/docker-compose.prod.yml

docker compose -f $C ps                          # 状态 + 健康
docker compose -f $C logs -f --tail=200 client-api
docker compose -f $C restart store-api
docker compose -f $C stop / start / down         # down 不删卷，数据安全

# 发版（只重建变更的服务）
git pull
docker compose -f $C up -d --build admin-api store-api client-api job

# 清理旧镜像（构建缓存和悬空镜像会持续吃磁盘）
docker image prune -f
docker builder prune -f
```

### 数据备份

MySQL 数据在具名卷 `shop-platform-prod_mysql-data` 里，`docker compose down` 不会删除，但 `down -v` 会。定时备份：

```bash
source docker/.env
docker exec shop-prod-mysql mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --triggers --databases shop_platform xxl_job \
  | gzip > backup_$(date +%F_%H%M).sql.gz
```

恢复：

```bash
gunzip -c backup_xxx.sql.gz | docker exec -i shop-prod-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD"
```

## 5. 排障

**应用起不来，日志报连不上数据库**
`docker compose -f $C logs mysql` 看 MySQL 是否 healthy。应用用的是 `application-docker.yml` 里的 `DB_HOST=mysql`（compose 服务名），如果改过服务名或网络，DNS 就解析不到。

**store/client/job 一直不启动**
它们 `depends_on: admin-api: service_healthy`。看 `docker compose -f $C logs admin-api`，通常是 Flyway 迁移失败（脚本冲突或库里已有不一致的 `flyway_schema_history`）。

**MQ 消息发不出去 / 消费不到（静默超时，没有报错）**
几乎总是 `ROCKETMQ_BROKER_IP` 的问题。broker 向 NameServer 注册的地址会被客户端直连；容器网络外的客户端拿到容器名/内网 IP 就连不上。检查：

```bash
docker exec shop-prod-rocketmq-broker \
  /home/rocketmq/rocketmq-5.3.1/bin/mqadmin clusterList -n rocketmq-namesrv:9876
```

`#Addr` 列必须是客户端能直连的地址。

**支付成功但订单一直是待支付**
`PAY_NOTIFY_BASE_URL` 必须是公网可达的 https 地址，且微信商户平台侧配置一致。微信回调打不到你的服务，本地日志里不会有任何错误——先用外网 curl 验证该地址可达。

**容器 healthy 但业务不通 / actuator 报 DOWN**
`docker exec <容器> curl -s localhost:<端口>/actuator/health` 看具体是哪个组件 DOWN。最常见是 Redis：Redis 开了 `requirepass` 而应用没拿到 `REDIS_PASSWORD` 时，日志里是 `NOAUTH HELLO must be called...`，应用能启动但 readiness 恒为 DOWN。四个应用的 `application.yml` 都读 `${REDIS_PASSWORD:}`（本地开发留空），compose 已统一注入。

**healthcheck 一直失败但服务其实是好的**
先手工跑一遍 healthcheck 命令：`docker inspect <容器> --format '{{json .State.Health.Log}}'` 看真实输出。RocketMQ 镜像里**没有 netstat/ss**，也没有 HTTP 端点，所以这两个服务的探针是读 `/proc/net/tcp{,6}` 找端口的十六进制（9876→`2694`，10911→`2A9F`）。改端口时要同步换十六进制值：`printf '%X\n' <port>`。另外 RocketMQ 绑的是 IPv6 通配地址，只查 `/proc/net/tcp` 会永远失败，必须带上 `tcp6`。

**RocketMQ broker 启动时抛 NullPointerException**
看似代码问题，实际是**卷权限**：新建的具名卷属 root，而镜像内 broker 以 uid 3000 运行，写不了 store 目录就在启动中途 NPE。compose 里的 `rocketmq-init` 服务（root 身份 chown 后退出）负责这件事，`docker compose down -v` 重建卷后它会自动再跑一次。不要图省事在 broker 的 command 里用 `su` 降权——`su` 会重置 PATH，镜像里的 java 随之找不到，报 `Please set the JAVA_HOME variable`。


**容器被 OOMKill（`docker inspect` 里 `OOMKilled: true`）**
`.env` 里四个 `*_JAVA_OPTS` 的堆之和加上依赖容器的内存超过了物理内存。JVM 已开 `UseContainerSupport`，但如果 compose 没设 `mem_limit`，JVM 按宿主机总内存的 75% 算堆，多个应用叠加就会超卖。内存紧张的机器要给每个服务加 `mem_limit` 并把 `-Xmx` 调到限额的 70% 以下。

> 实测提醒：在 8~16G 的开发机上同时构建 4 个后端镜像并运行整套 prod 栈，足以把 Docker Desktop 自身撑爆（进程直接消失、`docker` 命令报连不上 npipe）。分批构建（`up -d --build admin-api` 逐个来）或调小 `.env` 里的堆能避免。容器都带 `restart: unless-stopped`，Docker 重启后会自动恢复。

**磁盘满**
日志已按容器限流（50m × 5），最常见的元凶是构建缓存和 RocketMQ 的 store 目录。`docker system df` 看分布。

## 6. 尚未纳入本方案的部分

按需补充，当前 compose 不包含：

- **对象存储**：商品图/资质附件目前没有独立存储服务（MinIO / OSS），前端上传链路落地时需要补
- **HTTPS 与统一入口**：现在每个前端各占一个宿主端口。多租户按域名区分商城，生产需要在前面加一层 Nginx/Traefik 做泛域名证书（`*.${PLATFORM_BASE_DOMAIN}`）与统一路由
- **多副本与负载均衡**：单机单副本。要水平扩容需处理 RocketMQ 消费组、XXL-Job 执行器注册、以及 `admin-api` 的 Flyway 独占迁移（多副本时只能有一个实例跑迁移）
- **监控告警**：只有容器 healthcheck，没有 Prometheus/Grafana 与业务指标
- **CI 自动部署**：`.github/workflows/ci.yml` 只做构建与测试，镜像推送和远端发布未接
- **平台超管接口没有鉴权拦截器**：这是既有代码问题，与容器化无关。`shop-framework` 里只有 `ClientTenantFilter` / `StoreTenantFilter`，`/admin/**` 没有任何 filter/interceptor —— 实测不带 token 直接 `GET /admin/shops` 返回 200 和数据。`/admin/auth/login` 能正常签发 JWT，但没人校验它。**对公网暴露 admin 端口前必须先补上**，或在入口 Nginx 上做 IP 白名单兜底。
